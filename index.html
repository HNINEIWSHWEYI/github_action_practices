1. What is CI/CD?

CI — Continuous Integration

Every time code is pushed, an automated process checks it out, installs dependencies, and runs checks (tests, linting, type-checking) so problems are caught in minutes instead of being discovered later.

CD — Continuous Delivery / Deployment

Once code passes its checks, another automated process ships it somewhere — a server, a package registry, or, as on this page, GitHub Pages — without a human manually copying files around.

This repository demonstrates both: CI runs the Python test suite on every push, and CD publishes this static site.

2. What is GitHub Actions?

GitHub Actions is GitHub's built-in automation engine. You describe workflows as YAML files in .github/workflows/, and GitHub runs them on its own servers ("runners") in response to events like a push, a pull_request, or a schedule.

WorkflowOne YAML file = one automated process
EventWhat triggers it (push, PR, manual…)
JobA group of steps that runs on one runner
StepA single command or reusable action

3. Anatomy of a workflow file

Every workflow follows the same shape:

name: <shown in the Actions tab>

on:                     # 1. the trigger — what starts this workflow
  push:
    branches: [main]

permissions:            # 2. what this workflow is allowed to touch
  contents: read

jobs:                   # 3. one or more jobs, each on a fresh runner
  <job-id>:
    runs-on: ubuntu-latest
    steps:              # 4. the ordered steps inside the job
      - uses: actions/checkout@v4      # reuse someone else's action
      - run: echo "or run a raw shell command"

4. This repo's CI: running Python tests

.github/workflows/python-test_CI.yml checks the Python code on every change. Here's the actual file, followed by what each part does: 

name: Python Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests
        run: pytest -v
  1. Lines 3–7, on: — runs on push to main and on pull_request targeting main, so a PR gets its own red ✕/green ✓ check before it's ever merged.
  2. Lines 9–11, jobs.test — a single job named test, running on the ubuntu-latest runner.
  3. Lines 14–15, "Checkout code" — actions/checkout@v4 clones the repo onto that runner so later steps have the files.
  4. Lines 17–20, "Set up Python" — actions/setup-python@v5 installs the requested Python version (3.11) on the runner.
  5. Lines 22–23, "Install dependencies" — pip install -r requirements.txt installs whatever the app needs (currently just pytest).
  6. Lines 25–26, "Run tests" — pytest -v executes test_app.py. If any test fails, this step's exit code is non-zero, the job fails, and the commit/PR is marked with a red ✕ instead of a green ✓.

This workflow only checks the code — it never deploys anything. That's CD's job, below.

5. This repo's CD: deploying this page

.github/workflows/deploy-pages-CD.yml publishes this HTML file to GitHub Pages whenever it changes on main. Here's the actual file, followed by what each part does: 

name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
    paths:
      - "index.html"
      - "style.css"
      - ".github/workflows/deploy-pages-CD.yml"
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: "pages"
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Configure GitHub Pages
        uses: actions/configure-pages@v5

      - name: Upload site as Pages artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: "."

      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
  1. Lines 3–10, on: — runs on push to main, but only when the push touches index.html, style.css, or the workflow file itself (the paths: filter on lines 6–9, so editing app.py won't fire a redeploy) — plus workflow_dispatch on line 10, a manual "Run workflow" button in the Actions tab.
  2. Lines 12–15, permissions: — grants contents: read, pages: write, and id-token: write. That last one lets the job authenticate to Pages with a short-lived OIDC token instead of a stored secret.
  3. Lines 17–19, concurrency: — every run is queued under one group named "pages" with cancel-in-progress: false, so two deploys can never race each other; a new run waits its turn.
  4. Lines 21–26, jobs.deploy — the job runs on ubuntu-latest under a github-pages environment whose url (line 26) is filled in from the deploy step's output — that's what makes the live link show up in the repo's Deployments tab.
  5. Lines 29–30, "Checkout code" — same as CI, the runner needs the files to publish them.
  6. Lines 32–33, "Configure GitHub Pages" — actions/configure-pages@v5 detects the Pages settings for this repo (Settings → Pages → Source must be "GitHub Actions").
  7. Lines 35–38, "Upload site as Pages artifact" — actions/upload-pages-artifact@v3 packages the static files (this page, its stylesheet) as a deployable artifact from path: ".".
  8. Lines 40–42, "Deploy to GitHub Pages" — actions/deploy-pages@v4 takes that artifact, publishes it, and exposes the live URL as steps.deployment.outputs.page_url (this step's id is deployment, matching the environment url on line 26).

No build tools, no bundler — the "app" is just this HTML/CSS, so the CD pipeline's job is entirely about the process of shipping it safely.

6. Glossary

Runner
The virtual machine that executes a job (e.g. ubuntu-latest).
Action
A reusable packaged step, e.g. actions/checkout@v4. The @v4 pins a version.
Artifact
Files produced by one job and optionally passed to another, or deployed.
Secret
An encrypted value (API key, token) available to workflows without appearing in logs.
Environment
A named deployment target (e.g. github-pages) that can have its own rules and secrets.
workflow_dispatch
Lets you trigger a workflow manually from the Actions tab, with no push required.
